# Follow the evidence with investigative questions

Use this loop to decide which evidence question to pursue next while executing a root-cause
investigation. Turn observations and user challenges into testable explanations and
discriminating checks. A hot function or a plausible explanation opens another question;
it does not finish the investigation.

## Turn each answer into the next test

The useful questioning pattern is: establish what happened, locate the work, challenge the
explanation, find its history, inspect relevant changes, establish production applicability,
and identify a decisive test. Revisit earlier answers when new evidence changes them; this is
an inquiry loop, not a fixed sequence or a requirement to query every integration.

| Question to ask of the evidence | What the answer must distinguish | Owning method |
| --- | --- | --- |
| What exactly is observed, for which resource and time? | Alert lifecycle, measured resource pressure and customer impact are different observations. | The configured provider owner; [Parallel Grafana Investigation](../../parallel-grafana-investigation/SKILL.md) for Grafana. |
| What work accounts for the symptom? | A measured execution path versus a name, threshold explanation or inferred workload. | Parallel Grafana Investigation's profiling coverage. |
| What does the proposed explanation predict? | A testable hypothesis versus a renamed observation: parsing does not by itself establish replay, duplicate work or deadlock. | Source Investigation: trace the actual callers, scheduling, retries and progress conditions. |
| When was this behavior first observed, and did it recur? | Ordinary baseline activity versus an elevated signature, and earliest inspected evidence versus true onset. | The [profile behavior-onset search](../../parallel-grafana-investigation/references/profiling-coverage.md#locate-behavior-onset). |
| What differs in earlier, quieter or recovery windows and other instances? | A discriminating comparison versus an uncontrolled workload or sampling difference. | The relevant provider owner; preserve its comparison limits. |
| What changed near the observed transition? | Actual configuration or lifecycle events versus status snapshots, Git merges and temporal coincidence. | [AWS MCP](../../aws-mcp/SKILL.md) for AWS evidence; Source Investigation for source history. |
| Does the inspected code apply to the running artifact? | An immutable build/source relationship versus a matching tag or current branch. | Source Investigation's deployed-revision verification. |
| What evidence would confirm or weaken this mechanism? | Runtime execution of the candidate path versus static possibility. | Source Investigation plus the provider holding the required execution record. |
| What change addresses the demonstrated mechanism, and how would we verify it? | A proposed mitigation or conditional fix versus an implemented, validated remedy. | Source Investigation's causal path and validation proposal. |
| Can another reader check the answer and see the change? | Retrievable evidence and graph annotations versus unsupported prose or generic provider labels. | [Report Authoring](../../report-authoring/SKILL.md), with visual construction owned by Diagramming Style. |

For each unresolved material question, state the current observation, candidate explanation,
strongest alternative, the observation that would distinguish them, and the smallest authorized
read or test that could supply it. Reuse saved evidence first. Prefer a discriminating check
over collecting more examples of the same symptom. If it cannot be checked, retain that exact
gap and a conditional conclusion; do not upgrade the hypothesis to complete the story.

For example, a parser hotspot suggests asking for object/request identities and overlapping
enqueue/start/finish records before asserting duplicate replay. A restart-associated improvement
suggests checking the actual operation and what changed, not concluding which defect was cleared.
These are questions generated by the observations, not evidence that either mechanism occurred.

If a proposed source change is later than an already observed episode, use that temporal
counterexample before repeating the onset search. Ask for the candidate's actual apply time
and target, or object/request execution identities and progress that distinguish the mechanism.
More copies of the earlier hotspot do not establish why it ran or make a later merge its trigger.

When correcting a proposed explanation, state which behavior is observed and which mechanism
remains unproven, even if the immediate correction concerns timing. In the returned question
or change plan, name the receiving owners: Report Authoring for evidence/graph coverage and
Diagramming Style for visual construction. A graph suggestion without that handoff leaves
execution ownership unresolved.

Use [Report Continuation](../../report-continuation/SKILL.md) to retain the question, answer,
supporting evidence, correction and next unresolved check. Read-only investigation authority
does not authorize a fix, deployment, external message or publication. The linked owners keep
their query mechanics, scope restrictions, evidence semantics and verification; this reference
owns choosing and revising the investigative question, not their procedures.
